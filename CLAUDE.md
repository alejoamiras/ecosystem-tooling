# ecosystem-tooling

Bun monorepo consolidating Aztec packages under the `@alejoamiras` npm scope: `private-fee-juice` (the FPC + SDK, renamed from `aztec-fee-payment` — plan fee-payment-revisions-rename), `aztec-benchmark`, and `quota-paymaster` (the QuotaFpc quota paymaster extracted from dark-forest-aztec — plan quota-fpc-extraction; contract vendored byte-verbatim with a chain-verified class-id lineage, see its `known-deployments.json` + `verify:lineage`). Versions are LOCKSTEP with the Aztec version they target. `aztec-standards` lived here through 5.0.0 and was handed over to the Aztec Foundation (July 2026) — it is now [`@aztec-foundation/aztec-standards`](https://www.npmjs.com/package/@aztec-foundation/aztec-standards); the `@alejoamiras/aztec-standards` npm package is deprecated (all versions) and its trusted-publisher entry was removed.

## Current state

**Live** on npm, all provenance-attested and attestation-identity verified: **all three at `6.0.0` under `latest`** (released 2026-10-23 from `3e358bb`), targeting the stable Aztec `6.0.0` (`@aztec-labs/*@6.0.0` + `@aztec-foundation/*@6.0.0` — the two scopes version separately, see `config.aztecFoundationVersion`; aztec-nr `v6.0.0` from `aztec-labs-eng/aztec-nr`). `rc` still points at `6.0.0-rc.3`, and the Aztec 5 releases (`quota-paymaster@5.0.1-revision.2`, `private-fee-juice@5.0.1`, `aztec-benchmark@5.0.1`) stay installable by exact version. CI installs the Aztec toolchain only from digest-pinned files (`aztec-toolchain.lock.json` + `scripts/install-aztec-toolchain.sh`; the toolchain's npm tree is `npm ci` from the committed `aztec-toolchain/<version>/package-lock.json` with install scripts off (bcrypto, the one package without a prebuilt binary, is compiled from its locked sources against the running node's headers)). Everything publishes TOKENLESSLY through the OIDC `release.yml` (mode-based: release/rehearsal/revision; rehearse-then-release choreography with SHA binding + payload comparison). **Releases may now publish a SUBSET**: `packages=<pkg>` scopes a dispatch to one package, REQUIRED in revision mode (the `-revision.N` counter is per-package history) and proven end to end by quota-paymaster's 5.0.1-revision.1 and .2, each of which left the other two untouched. Its tag is name-qualified (`quota-paymaster-v5.0.1-revision.1`) — so is a subset rehearsal's canary tag, which the cleanup step must use. Consolidation, the 5.0.0 stable migration, the standards-handover/5.0.1 plan, the quota-fpc-extraction plan (six-round codex audit: accept) and the quota-operator-cli plan (operator CLI + config-module signer pattern + subset revisions; 23 review rounds, 124 findings) are all COMPLETE (plans local-only under `implementations-plan/`; audit under `audit/security/`). `docs/roadmap.md` tracks what's next; `docs/ci-pipeline.md` has the full release runbook — including the honest scope of the TS-only revision guarantee (`verify:lineage` pins the class id to an in-repo constant from the SAME commit: a review-gated tripwire, not a cross-version proof).

## Commands

- `bun install` — 7-day min-age supply-chain gate active (bunfig.toml); only the `@aztec-labs/*` / `@aztec-foundation/*` names still inside the window are excluded, regenerated by `bun scripts/bump-aztec.ts --regenerate-excludes` (empty once a release clears it)
- `scripts/install-aztec-toolchain.sh <version> [AZTEC_HOME]` — installs the Aztec toolchain only from inputs sha256-pinned in `aztec-toolchain.lock.json` (linux-x64; CI's only install path). Use an isolated `AZTEC_HOME` locally. After a bump, regenerate its entry with `bun scripts/lock-aztec-toolchain.ts <version>` and review the diff: it also writes `aztec-toolchain/<version>/` (the npm lock, refused unless every package is a public-registry tarball at least 7 days old, Aztec-scoped ones at their lockstep version excepted) and its `npmLock` pin
- `bun run lint` / `lint:fix` — biome + sort-package-json
- `bun run lint:actions` — actionlint (run before pushing workflow changes)
- `bun run typecheck` — full-surface tsc (src + tests + benchmarks + scripts, all packages)
- `bun run test:nr` — Noir TXE tests per package (`aztec test`); count floors: fee-payment 11, quota-paymaster 20. NEVER run concurrently with a live local network (LMDB flakes)
- `bun run test:js` — private-fee-juice: vitest integration against `aztec start --local-network` (node :8080, L1 :8545; override via `NODE_URL` / `L1_RPC_URL`). quota-paymaster: unit, then integration on a self-provisioned disposable network (it warps past each paymaster's 1h bootstrap); `test:unit` is network-free. The disposable-network suites take the toolchain from `$AZTEC_HOME` (default `~/.aztec`) at root `config.aztecVersion`
- `bun run test:warp` — quota-paymaster's time-travel suite; self-provisions its OWN disposable network (ephemeral ports + own anvil), safe alongside a shared one. Never widen the main vitest include to discover warp tests
- `bun run bench` — aztec-benchmark suites (local network required)
- `bun packages/quota-paymaster/scripts/cli.ts <deploy|policy|bridge|claim|measure>` — the operator CLI from source; the PUBLISHED equivalent is `npx @alejoamiras/quota-paymaster <cmd>`. Needs `--config-module <path>` (a module you write that supplies the signer); state-changing commands print an ActionPlan digest and do nothing without `--yes`
- `bun run --cwd packages/quota-paymaster verify:lineage` — binds quota-paymaster's vendored sources + dep lock + artifacts to the class id anchored for `config.aztecVersion` in `known-deployments.json` (chain-verified for 5.0.1 on mainnet and for 6.0.0 on the public testnet, the latter as its `compiled` entry's `verification` block — address, network, date; a `compiled` entry claiming `verifiedAgainstChain` without a complete block counts as unverified. Other versions are local pins under `compiled`, and an entry's `localNodeVerification` records that CI's `class-id-chain` test read that class back from a local node, not a public chain); run after ANY contract-side change

## Hard conventions (from the approved plan)

- **Aztec version single source of truth**: root `package.json` `config.aztecVersion` (the `@aztec-labs/*` pins and our own package versions) plus `config.aztecFoundationVersion` (the `@aztec-foundation/*` pins; upstream versions that scope separately since 6.0.0-rc.3, which depends on foundation 6.0.0-rc.6). Never hand-edit either. Bumps ONLY via `bun scripts/bump-aztec.ts <version> [--dry-run]`, which derives the foundation version from `@aztec-labs/aztec@<version>`'s own deps and refuses unless the whole registry closure agrees. It sweeps package.json pins, Nargo.toml tags, PRD header; regenerates bunfig exclusions; emits an alias-aware supply-chain report) + `scripts/verify-nargo-refs.sh --write` (commit-locks every Nargo git tag, transitively through aztec-nr's own git deps; verified on every release build). A new Aztec version also needs a reviewed `compiled[<version>]` class id in quota-paymaster's `known-deployments.json`.
- **Internal cross-package deps: exact lockstep pins, NEVER `workspace:*`** (npm CLI publishes the protocol string verbatim — breaks consumers).
- **Published manifests are curated**: no lifecycle scripts, `@aztec-labs/*` / `@aztec-foundation/*` as exact peerDependencies, each at its own scope's config version (legacy `@aztec/*` only as the `npm:@aztec/viem` alias), `repository` must point at THIS repo (provenance validates it). `scripts/lib/manifest-policy.ts` enforces this on the overlay and on the packed tarballs, and `lockfileScopeErrors` (run by `test:scripts`, `verify-tarball` and `--regenerate-excludes`) fails if `bun.lock` resolves an Aztec-scoped name to another version or any locked package declares one, so an `overrides` entry cannot force a foundation version the labs release never asked for.
- **Publish order: benchmark → fee-payment → quota-paymaster** (quota-paymaster has no internal runtime deps; appended LAST; first-published at 5.0.1 via the one-time bootstrap 2026-08-07 — its trusted publisher exists, all three publish tokenless). rc versions (`X.Y.Z-rc.N`, `mode=release`, only when equal to `config.aztecVersion`) get the `rc` dist-tag, never `latest` — the publish job asserts `latest` unchanged and refuses to move `rc` backwards; repo-side improvements to a published lockstep version (security fixes, doc-visible corrections — the version is locked to Aztec so it can't be bumped) ship as `<version>-revision.N` via `mode=revision` (dist-tag `revision`; pass `set-latest=true` to publish the revision under `latest` at publish time, else `latest` is moved manually with OTP). `-revision.N` sorts below its base and `^`-ranges won't match it — adopting consumers must pin exactly, so deprecate the superseded base version. A revision of an rc is `X.Y.Z-rc.N.revision.M` (only while `config.aztecVersion` is that rc): it publishes under `rc`, sorts between its base and the next rc so `^X.Y.Z-rc.N` and `@rc` reach it, and `set-latest` is refused. Policy lives in `scripts/release-policy.mjs` (tested by `node --test`).
- **Releases go through the rehearse-then-release choreography** (docs/ci-pipeline.md runbook): rehearsal publishes `0.0.0-canary.g<sha>` through the REAL release.yml; the release then binds to that commit (`expected-head-sha`) and byte-compares against the rehearsed tarballs (`compare-against`). Never relax the fail-closed tarball assertions.
- **Keep vitest** for migrated suites (forks pool + inline @aztec deps are load-bearing); bun replaces yarn as PM/script-runner only.
- Noir formatting via `aztec-nargo fmt` (pre-commit hook); TS/JSON via biome.
- Workflows: per-package gates with internal `changes` path-filter job (never trigger-level `paths:` — deadlocks required checks). Each package workflow ends in an always-run `<Name> Status` job, which main's ruleset requires: a new job joins its `needs`, and a job that another non-status job needs stays unconditional (`scripts/status-gate.test.ts`; docs/ci-pipeline.md § Required checks). `actions/*` may use major tags; ALL other actions full-SHA pinned.
